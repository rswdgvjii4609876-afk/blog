# 面试演示与理解检查

## 演示前

1. 准备 Java 21 JDK，检查 `java -version` 和 `javac -version`。
2. 运行 `bash mvnw verify`（Windows 使用 `mvnw.cmd verify`）。确认测试通过。
3. 启动应用，打开浏览器中的本机 8080 端口。不要依赖面试现场重新下载依赖。
4. 若已经有自己的文章，先停止应用并备份 data 文件夹。不要删除或重置自己的数据来演示。

## 约 6–8 分钟的演示路线

1. **定位（30 秒）**：这是“知行”学习博客。保留题目的基本功能，用 Markdown 和文章成长记录体现持续复盘。
2. **写作（1 分钟）**：从后台新建文章，填写标题摘要、`## 小节`、引用和 Java 代码块，预览并保存草稿。
3. **隔离（30 秒）**：后台可见草稿，首页搜索不到；直接访问其公开详情返回 404。
4. **发布（1 分钟）**：编辑并发布，演示目录、代码高亮、复制、标题/摘要搜索及无匹配状态。
5. **成长记录（1 分钟）**：修改正文、填写修改说明，查看时间线与历史内容；恢复旧版，说明“保留历史且恢复为草稿”的取舍。
6. **并发保护（1 分钟）**：两个标签页打开同一篇文章，先保存一个，再保存另一个；展示冲突提示和保留的输入。
7. **持久化（30 秒）**：重启应用，文章和历史仍在；示例文章不会重复插入。
8. **交付证据（1 分钟）**：展示 Git 阶段提交、测试报告、CI 配置和 README，说明真实遇到的困难。

删除演示应使用临时文章：先取消，再确认永久删除。不要对自己的重要文章演示。

## 需要自己讲清楚的问题

- 为什么公开详情不能仅在模板里隐藏草稿？→ 必须在数据库查询条件中限制状态。
- 为什么恢复不直接覆盖历史？→ 恢复本身也是一次修改，留下回溯和撤销的空间。
- 为什么恢复为草稿？→ 历史可能含有已经撤回的内容，不能因为恢复就意外公开。
- 为什么要 Service 和事务？→ 文章与历史应一起成功或一起回滚，Controller 不应编排多表写入。
- version 检查与 `@Version` 分别解决什么？→ 前者处理旧页面，后者覆盖检查之后仍可能发生的并发写入。
- 为什么用了 Markdown 还要清洗？→ 输入仍然不可信，原始 HTML、危险链接等必须统一处理；预览也不能例外。
- CSRF 是否能保护任何人无法访问后台？→ 不能；此项目没有登录，默认只用于本机开发。
- H2 文件库与内存库有什么区别？→ 前者重启保留数据；后者用于独立、可重复的自动测试。
- 为什么 Git 记录分阶段？→ 让需求、实现、验证和修复可追溯，而非补造开发过程。

## 如实说明 AI 协作

可表述为：“我使用 AI 辅助设计、实现和排查；每项功能通过测试和浏览器流程验证。我能解释主要代码和取舍，也保留了没有实现的边界。”
不要把尚未理解的实现说成自己已经掌握。建议在面试前亲自完成一次独立修改，例如新增一条校验并编写测试，确认理解请求到数据库的完整路径。
